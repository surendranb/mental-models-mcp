# Cynefin Framework

## 1. Core Principle
Problems belong to one of four domains: Clear (cause and effect known), Complicated (cause and effect discoverable via expert analysis), Complex (cause and effect only understood in retrospect), or Chaotic (no cause and effect discernible). Applying the wrong management strategy to a domain guarantees failure.

## 2. When NOT to Use (Failure Boundaries)
- Purely deterministic, formulaic calculations.
- Over-classifying straightforward procedural tasks.

## 3. Operational Thinking Steps
1. Diagnose the Domain:
   - Clear: Sense -> Categorize -> Respond (Follow SOP / Best Practice).
   - Complicated: Sense -> Analyze -> Respond (Hire experts, conduct trade studies).
   - Complex: Probe -> Sense -> Respond (Run small experiments, safe-to-fail prototypes).
   - Chaotic: Act -> Sense -> Respond (Take immediate decisive action to stop bleeding, then assess).
2. Align Response Protocol: Do not try to plan or specify a Complex problem with waterfall requirements; run iterative probes.

## 4. Diagnostic Probing Questions
- "Are we treating an unpredictable Complex problem as if it were a predictable Complicated engineering task?"
- "Can this system be planned, or must we run probes to see how it responds?"

## 5. Worked Example
- Context: A company spent 9 months writing a 200-page specification for a brand-new, never-before-seen AI product feature (acting as if it were Complicated).
- Correction: Reframed as Complex: built 3 small weekly prototypes, put them in front of 20 users, observed behavior, and converged on the winning design in 3 weeks.
